## P0【B】HERE Route Matching API 企业版门控 — 选型转向 Routing /import

### 症状
设计阶段计划调用 HERE Route Matching API v8（`routematching.hereapi.com/v8/match/routelinks`），用 Base Plan freemium key 实测返回 HTTP 403/429，`X-RateLimit-Limit: 0`。

### 根因
HERE 平台自 **2025-03-15** 起将 Route Matching API v8 调整为 **Enterprise Plan 独占**。Base Plan key 的配额直接为 0——不是限流，是功能门控。

### 影响
- 原方案"逐点 linkId + confidence + matchedCoords"不可用
- 需要找到 Base Plan 内的等价能力

### 解决方案
改用 **Routing API v8 `/import`**（`router.hereapi.com/v8/import`）：
- 输入：JSON body `{"trace":[{lat,lng},...]}`（2–50,000 点）
- 输出：路线级 sections[].polyline（flexible polyline）+ summary
- **逐点偏差需客户端自算**：自建 `decodeFlexiblePolyline` 解码 + `nearestOnPolyline` 垂足投影 → `deviationM`
- linkId 仅 section 级（非逐点）

### 商业意义
- Base Plan 即可完成 PoC 评估——降低客户评估门槛
- `v8/match` 的逐点置信度是 Enterprise tier 的卖点：客户 PoC 阶段用 `/import` 测出匹配质量，量产需要逐点 linkId 时自然升级
- **方案架构师提前踩到这个坑 = 给客户做 PoC 时避免重复踩**

### 一句话教训
**云服务商的计价梯队调整会直接改变技术方案选型——PoC 设计前必须实测 API 可用性，不能只看文档。**

## P9【S+】北向上实为南向上 — "方向相反"族谱的终章

### 症状
0096 北向上模式车标与移动方向恒相反；车头向上一致正确。

### 时长
当日诊断 ~3h。但它是 **七次发作族谱**（09-09 → 09-17）的最后一次：KITTI yaw → 航向公式 → 航向源 → 引擎定律推论，跨四个层、五个会话。

### 代码量
**2 行**（heading 0→180 ×2 处）+ ~30 行测试。

### 根因
HERE Maps JS API 3.1 引擎实测定律：**R = 180° − h**（传 heading h → 地图内容旋转 180−h 度）。因此 `heading:0` 渲染的是**南向上**而非北向上。09-16 已实测出定律本身，但其推论"h=0=北向上"从未被验证——而地图倒置被道路网近似对称性伪装，无人读街道名。

### 为什么难（四个结构性原因）

1. **1-bit 症状 × 五层符号系统**：数据约定（KITTI yaw 0=东逆时针）/ 数学（yawToCompass 转换）/ 公式（compassDeg 计算）/ CSS（transform rotate）/ 引擎（heading 语义），任何一层翻转都是同一症状"方向反了"；
2. **抵消性错误**：地图翻转 180° × 公式多加 180° = 车头向上完美正确——每修好一层就暴露下一层，洋葱式复发；
3. **验证通道全失效**：
   - 视觉模型判断箭头角度 ±50° 且自相矛盾 → 禁用
   - 无头浏览器无 WebGL → 无法测渲染
   - 有头探针 Tangram 场景也起不来 → 只能测 DOM 几何
   - 旋转互相关探针两次推反符号 → 仪器自身有 bug
4. **验证了错误命题**："A/B diff=0" 被记录为"北向上已验证"——它只证两条路径渲染相等，两个南向上同样 diff=0。

### 解决方案
1. 用户 2-bit 判别观察（北向上反/车头向上对）→ 代数强制解：北向上必须翻转 180°
2. 逐层排除：离线数学杀切线、代码审查杀底图/祖先链
3. **geoToScreen 数值探针**：运行时包装 `H.Map` 构造器捕获实例，不依赖渲染，0/90/180/270 × N/E/S/W 十六点直接测出引擎传递函数 R=180−h 精确成立
4. 修复：北向上 `heading: 0 → 180`；建图期 bounds 调用同带 `heading: 180`（analysis 模式无相机跟随 effect，那是唯一航向写入点）

### 防线
`mapview.test.tsx` 回归锁：heading=180 断言（判别性取值 yaw=180，在两种公式下结果不同）

### 一句话教训
**多层旋转变换的总符号是各层符号之积——某配置"看起来对"可能恰是两个错误相乘为正。必须对每层单独测符号，而不是只测合成结果。**

## P5【S−】车标抖动三因叠加

### 症状
回放中车标抖动/闪跳/脱路；baseline（60fps 浮点）与当前树（10Hz 门控）都抖——排除渲染节奏假设。

### 时长
09-15 全天 + 次日收尾。含 P2 纯几何方案三连败。

### 代码量
~650 行（matchedTrack.ts 240 + 测试 157 + derive/types/fixtureStore/App/MapView/playback 接线）。

### 根因（三因叠加，互相伪装）

| 因 | 根因 | 量化证据 |
|----|------|----------|
| ① 垂足闪跳 | MM 响应是地理不相连碎片（断口最大 73m，拼接序≠驾驶序），逐帧全局最近投影单帧闪跳 | 5–73m/帧，折算车速数百 m/s |
| ② DR 步伐游走 | dispSpeed 门控在两种速度源间切换 → 步长 CV 45% | 0.33↔0.84m 摆动 |
| ③ 引擎相位差 | HERE 3.1 DOM marker 与相机 setCenter 走不同更新路径 | 用户判别"地图平滑、车标独抖" |

### 过程要点

**先量化再动手**（三条证据链）：
1. 垂足闪跳：离线复刻全管线，逐帧 nearestOnPolyline 量化
2. DR 步伐：`deadReckon` 输出弧长步长统计
3. 静止期：0.11m 步/rAF p50=16.7ms（渲染层无瓶颈）

**P2 纯几何方案三连败**（均被量化否决）：
- 粘滞方案：p90 1.4m, 60 次杂步
- 到访序方案：p90 3.4m, 96 次杂步
- 单调弧长方案：section 重访使回退 62 处，结构不可行

核心教训：**几何连续 ≠ 运动学连续**。

### 解决方案
1. **运动学门控序列匹配**（`matchedTrack.ts`）：
   - 到访序拼装 + 断口桥 + Chaikin 折角圆化
   - 预测 `arc += v×dt`，拒绝门 `max(1.5×v×dt, 5m, 0.5×v)`
   - 门内弱锚定 `g=0.08`，超门 coast，持续 8 帧重绑 + 锁定 50 帧
   - 重绑跳变摊成 8m/帧掠过（消瞬移）
   - 5 点中值平滑
2. **车标改钉相机中心的 DOM 叠层**（结构性消灭双路径）：不用引擎 marker，用 `<img>` 叠层钉在容器 67% 高度（134% 宿主 div 的中心 = 相机中心）

### 附带小修
- 叠层锚点 50%→67%（脱路 150px）
- 图标异步解码改 `<img>` 内联
- 合成测试数据物理自洽（0.001°/帧被滤波器当 730m/s 拒绝）

### 一句话教训
**多因症状必须先建立量化证据链再分因治理；被否决的方案族（纯几何连续性）要记录否决理由，防止三次踩同一坑。**

## P7【A】车头向上圆圈/道路名抖动（含两次回归）

### 症状
车头向上播放中 GNSS 圆圈全体微抖、0096 >38s 道路名微抖，暂停即止。

### 根因
heading-up 用「外层 CSS rotate+2.3×scale 宿主」实现，引擎按未旋转坐标系整像素重定位 DOM marker/矢量标签——双路径互搏被放大（与 P5③ 同族）。

### 解决方案
删 CSS transform/scale，改引擎原生 `setLookAtData({ position, heading })` 逐帧驱动——瓦片、marker、标签同管线渲染。

### 回归 1（勿重蹈）
`lookAtData` 平移字段误用 `center`，被引擎**静默忽略** → 车标原地转圈不前进。
**教训**：v3.1 契约字段是 `position`（H.geo.Point）；假 H 测试当时与代码同错了假设——测试必须断言真实契约字段。

### 回归 2（勿重蹈）
航向公式按被污染的 0093 IMU 基准拟合 → 错误定律 → 用户实测否决。
**教训**：校准基准必须先证明纯净。

### 一句话教训
**引擎/框架的"静默忽略"是回归温床——契约字段要进测试；替换渲染路径时旧路径的隐性假设全部要重新验证。**

## P8【A】航向源绑路（IMU 漂移确诊）

### 症状
用户再报两模式航向与行驶方向相反/差 60°（0096）。

### 根因
0093 数据集 IMU headingDeg 漂移 4→180°（"真值不可信"）；0096 IMU↔位移吻合 0.1°。

### 解决方案
航向源改**轨道切线**（`trackTangentBearing`，与位置同源，构造性贴路）+ 位移方位回退。

### 过程要点
三轮用户判别实验拟合引擎定律（传 B→正下；传 360−B→差 60°=2B−180；传 B+180→朝上）——**每轮消掉一半假设空间**。旋转互相关探针两次推反符号 → 确立"仪器只做 DOM/数值层，方向类结论必须用户目视终验"。

### 一句话教训
**传感器/数据源退化要先定量判别（漂移曲线）再决定采信策略；判别实验设计的目标是信息量，不是数量。**

## P1【B】KITTI yaw 约定 — 族谱第一章

### 症状
车标航向恒偏（0033 偏 15.6°、0011 偏 59.5°）。

### 根因
`headingDeg` 实为 KITTI oxts yaw（0=东、逆时针），被当罗盘角（0=北、顺时针）消费。

### 为什么这次干净
有对照通道——坐标反算真航向 vs 图标航向，两轨迹 100% 点位误差 ≤5°，一次锁定公式 `compass=(90−yaw)%360`。

### 一句话教训
**外部数据字段命名 ≠ 语义；有 ground-truth 反算通道时，约定类错误半小时可杀。**

## 额外问题：0042 隧道 60/120s 车标乱跑

### 症状
0042 模拟隧道选 60s/120s，Demo 开始 ~2s 后车标乱跑；30s 档正常。

### 根因
长拒止期 DR 漂移 67m，恢复期抖动使逐帧投影在**地理贴近的相邻 section 间闪跳**（桩段贴主段尾 ~40m）→ 到访序列出现伪重访 `[主,桩,主,桩]` → `assembleTrack` 按重访复制主段 → **7018m 幻影轨道**（真值 2586m 的 2.7 倍）→ 帧 0 锚错副本（弧 4488 而非 ~0）→ 车标倒行 + 横穿 2.4km 幻影断桥。

**轨道本为对抗投影闪跳而生，但拼装轨道的到访序列自己消费了闪跳——蛇吞尾。**

### 被否决的路线
- F1「noFix 帧不入 router 请求」：router 对 30s+ 空洞返回残缺路线（1004m vs 真值 2586m），DR 融合输入其实在帮 matcher 铺满全程
- 「体叠放三明治判据」：实测两段是 ~40m 平行贴近非叠放，前提不成立（合成几何锁住的是错误前提）

### 解决方案
`dropStalledRevisits`：重访游程的**段内跨度**（首末帧投影弧长差）< max(8m, 5%×段长) 判为停滞伪重访，不复制几何。跨度判据用真实数据标定（伪重访 0-73m vs 真重驾 295m/96%）。

## 额外问题：0042 关隧道 t≈34s 车标一顿一顿

### 症状
0042 关隧道 Demo t≈34s 起顿挫；放大仍顿、双倍速相同（排除渲染像素量化）。

### 根因
DR 是 10Hz 预测/1Hz 锚定——高速下 1s 积分误差累积成**单帧 12.8m 级锚定跳变**（0042 25.6m/s；0096 8m/s 仅 ~3m）> 5m 拒绝门 → 拒绝→重绑 ~1Hz 循环 → "平滑-猛跳"节律。

### 被否决的路线
- 渲染像素量化（用户判别实验直接杀死——放大仍顿）
- 观测中值预平滑（锯齿是周期性台阶，中值只延迟透传，RED 测试证伪）
- 观测均值预平滑（可完美滤 1Hz 但会抹平真实换段尖峰）

### 解决方案
拒绝门加 **DR 1Hz 锚定余量项 `0.5×v`**（1s 积分误差当量）：0096（4m<5m）与 0093（5-7.5m≈原值）不受影响，0042（12.8m）恰好容纳锯齿且仍拒绝 67m 级真实异常。

## 横向元教训（跨问题模式）

### 1. 挑战与代码量负相关于诊断难度
P9（2 行/三天/七次发作）vs P10（400 行/一天/一次过）。排期时"看起来简单"的症状（1-bit 布尔类）恰恰要预留最长的诊断预算。

### 2. 一个症状 ≠ 一个 bug
七次"方向相反"是四个层的四次不同故障 + 三次修复的副产物。复发不一定是"没修好"，可能是洋葱剥到下一层——每次复发都要重新走根因流程，禁用"上次就是这么修的"记忆捷径。

### 3. 验证通道的可信度要先于验证本身被验证
本工程的通道淘汰史：
- 视觉模型（±50°，禁）→ 截图（白板幻觉，加 ≥300KB 门槛）→ 无头浏览器（无 WebGL，禁）→ 有头探针（Tangram 场景挂，仅 DOM 几何可用）→ **geoToScreen 数值通道（终器）**

仪器建设花的每一分钟都在后续问题里连续复利。

### 4. 验证结论不得强于实验实际证明的命题
"diff=0"≠"北向上"；"heading-up 对"≠"方向族关闭"。写结论时把实验证明了什么和推断了什么分开记录。

### 5. 校准/对照的基准要先证纯净
0093 漂移 IMU 作为基准产出了错误定律，成本是一整个用户往返轮次。

### 6. 外部黑盒与文档矛盾时，测传递函数、钉回归测试、停止再读文档
R=180−h 现在是 `mapview.test.tsx` 里的硬编码契约。

### 7. 角度/方向代码没有直觉护栏
三次仪器或助手翻符号——任何角差/方位助手必须先用手算样例自证再用。

### 8. TDD 的判别性取值
yaw=90（compass=0）在两种公式下同值 → 假绿；yaw=180 才能区分 270 vs 90。写测试先检查取值能否区分实现空间。

### 9. 用户判别实验是最便宜的高信息通道
"地图动还是车标动"（P5）、"哪一模式反"（P9）各一击定位层级。设计成 2-bit 问题（是/否 × 两模式），一次消一半假设空间。

### 10. 定性结论绑定环境前提
同款报错在 StrictMode dev 是噪声、在探针 profile 是真死。

### 11. 引擎抖动族谱的统一规律（P5③ → P7 → P15）
HERE 3.1 的瓦片/marker/标签各有独立的像素对齐与重定位路径。任何导致"同一帧内引擎更新多次"或"多路径写同一像素"的机制——DOM marker vs 相机（P5③）、CSS 旋转放大（P7）、两步 setLookAtData（P15）——都会在亚像素尺度产生可见抖动。**修复方向统一为减少引擎每帧更新次数/路径数**，而非在多路径上做补偿。

## P13【C+】播放结束后车标浮在下 1/3 处不动

### 症状
Demo 模式播放结束或暂停后，用户移图或缩放地图时，车标始终停在画面下 1/3 处，不在车标的真实地理位置。

### 根因
车标 DOM 叠层是**屏幕空间元素**（`position: absolute; top: 67%`），只在相机锁定跟随时与地理坐标对齐。播放结束后相机不再跟随，但 DOM 叠层还钉在屏幕 1/3 处——地图移走了，叠层没动。

### 解决方案
新增 `playing` prop 驱动两种渲染范式切换：

| 状态 | 车标渲染 | 相机 | 用户操作 |
|------|----------|------|----------|
| 播放中（playing=true） | DOM 叠层 @ 67%（消抖动） | 锁定跟随 | 不能自由移图 |
| 暂停/结束（playing=false） | HERE marker @ 真实位置 | 不锁定 | 可自由平移缩放 |

### 一句话教训
**屏幕空间叠层（DOM）和地理空间元素（引擎 marker）是两种不同的渲染范式——切换时机要显式驱动，不能让一种范式"泄漏"到不适用的状态。**

## P14【C】进入 Demo 模式未播放时车标不可见

### 症状
点击 Demo 模式 tab 后（未按播放），地图停在建图期的全轨迹视野（zoom ~14），车标不可见，需手动缩放才能找到。

### 根因

### 解决方案

**引入状态分支时，检查每个分支的"初始进入"路径——从 Analysis 切到 Demo 是 mode 变化，但新分支需要自己处理定位。**

## P15【C+】播放时街道名抖动——两步 setLookAtData 双重重定位

### 症状
Demo 播放中地图街道名（矢量标签）微抖。暂停时不抖（暂停态已切 HERE marker + 单步 setLookAtData）。

### 根因
播放态相机 effect 每帧调用**两次** `setLookAtData`：① `{ position: 车标坐标 }` 定位车标；② `screenToGeo(w/2, h/3)` 算偏移后再 `{ position: 偏移坐标 }` 把车标推到画面下 1/3。引擎每帧双重视口更新 → 街道标签按整像素对齐重定位两次 → 可见抖动。

与 P5③ / P7 同族（引擎内外双路径互搏），但这次不是 marker vs 相机，而是**同一管线的两次调用**之间的亚像素差异。

### 被否决的路线
合并两步为一步（直接算偏移坐标）——`screenToGeo` 依赖引擎当前视口状态，第一次调用改变了视口，第二次 `screenToGeo` 读到的是更新后的视口；合一步无法用 `screenToGeo`（它需要引擎已定位后的屏幕坐标）。

### 解决方案
恢复 **134% 宿主高方案**（09-15 P3 已验证）——宿主 div 高度 = 容器高度 × 134%，HERE 地图引擎的相机中心自然落在宿主中点 = 容器 67% 高度处。DOM 叠层钉在 `top: 67%` 与相机中心重合。单步 `setLookAtData({ position: 车标坐标, heading })` 即达导航布局——无需 `screenToGeo` 第二步，引擎每帧只重定位一次，街道标签稳定。

### 134% 方案的代价
宿主 div 比容器高出 34%，底部 34% 的地图内容被 `overflow: hidden` 裁掉——但相机中心在 67%，可见区域以车标为中心上下各 ~50%，实际可见范围不受影响。

### 一句话教训
**引擎每帧的 setLookAtData 调用次数要最小化——两次调用即使参数连续，引擎内部的视口更新/像素对齐也会产生亚像素差异，放大为可见抖动。134% 宿主高是 HERE 3.1 的经典导航布局技巧：用 DOM 尺寸偏移相机中心，避免代码层面的二次位置修正。**

## 引擎抖动族谱统一视角

P5③ → P7 → P15 三次抖动同族，根因都是"引擎多路径/多调用的亚像素差异被放大"：

| # | 抖动源 | 修复方向 | 共性 |
|---|--------|----------|------|
| P5③ | 引擎 marker vs 相机 setCenter 双路径 | DOM 叠层替代引擎 marker | 减少路径数 |
| P7 | CSS rotate+scale 放大整像素重定位 | 引擎原生航向替代 CSS 旋转 | 减少路径数 |
| P15 | 同管线两次 setLookAtData | 134% 宿主高替代两步调用 | 减少调用次数 |

**统一规律**：HERE 3.1 的瓦片/marker/标签各有独立的像素对齐与重定位路径。任何导致"同一帧内引擎更新多次"或"多路径写同一像素"的机制都会在亚像素尺度产生可见抖动。修复方向统一为**减少引擎每帧更新次数/路径数**，而非在多路径上做补偿。

## P16【C+】分析模式视野不完整 + 播放缩放限制

### 症状
Analysis 模式下轨迹起点/终点/DR 点贴边甚至超出视野；播放时无法缩小到 zoom 17 以下看更大范围。

### 根因（三因叠加）
1. **宿主高 134% 在 Analysis 模式也生效**——为 Demo 导航布局设计的 134% 宿主高在 Analysis 模式下导致引擎以为视口比实际大 34%，底部内容被 `overflow: hidden` 裁掉；
2. **bounds 只算 trace + derived + drPath**——gnssPath 散点、carTrace（DR 增强轨迹）、carTrack（车标轨道）的远点不纳入，起点/终点贴边；
3. **`if (zoom < 17) setZoom(17)`**——09-15 为补偿 CSS scale 移除而设的下限，134% 宿主高方案下不再需要。

### 解决方案
1. 宿主高条件化：`carPos !== undefined ? '134%' : '100%'`——Demo 134%（相机中心在 67%），Analysis 100%（bounds 居中不被裁）；
2. bounds 纳入全部图层：trace + derived + drPath + gnssPath + carTrace + carTrack.path；
3. 去掉 zoom 下限，用户播放时可自由缩小；
4. bounds 四周扩 8% 余量（`dLat/dLng × 0.08`，退化场景 `|| 0.001` 防零跨度），起终点/DR 点不贴边。

### 一句话教训
**为一个模式设计的全局参数（134% 宿主高 / zoom 下限）在另一个模式下会变成 bug——模式特有参数要条件化，不能无差别应用。**

## P17【C+】播放中滚轮缩放失效（10-20）

### 症状
Demo 播放中滚轮缩放几乎无效（探针合成 8 格滚轮，zoom 仅 +0.27，龟速爬）；暂停时完全正常（+3.6）。用户在线报障，本地 dev 复现——非线上特异，当前树即存在。

### 根因
播放跟随相机的每帧 `setLookAtData({position,heading}, false)`（60Hz）不断**打断**原生 `H.mapevents.Behavior.WHEELZOOM` 的缩放动画——滚轮触发的是"趋向目标 zoom"的动画进程，而 setLookAtData 每帧重置视模型状态，在途动画被丢弃。zoom 值本身不丢（P16「不传 zoom」保住了值，snap-back 已修），但动画永不完结，只剩帧间隙零头。**P16 是同一交互路径上的同族残余**：当时只验证了「不传 zoom 不 snap-back」（值层面），没验证「动画能否走完」（进程层面），验收手段停在调用参数断言。

### 解决方案
不与引擎动画抢时间：播放中 `behavior.disable(WHEELZOOM)` 关闭原生动画式滚轮缩放，宿主 div 挂 `{passive:false}` wheel 监听，调 `setZoom(±0.5, animate=false)` **无动画同步步进**——立即生效，下一帧 follow 不携带 zoom 而无从打断；暂停 `enable` 恢复原生的平滑动画缩放（该路径实测健康，不动）。建图 effect 重建 behavior 时按当时 playing 同步一次，堵「重建后原生通道复活」窗口。~15 行 + 测试 ~80 行，~2h（含 Playwright 探针定量诊断：修复后播放 +3.87 / 暂停 +5.0，本地与线上逐项一致）。

### 一句话教训
**修复「值被覆盖」类症状后，必须对同一交互路径做端到端数值验收（合成 N 格输入 → 读引擎状态真值），只验调用参数会漏掉「不丢值但进程被打断」的形态。**
