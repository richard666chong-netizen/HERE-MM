## 二、关键概念（演示口径，别被追问打穿）

- **隧道是场景参数，不是数据**：轨迹/航向/速度/加速度全是真实 KITTI oxts；只有「GNSS 被拒止多久」是设定值。
  界面上的 `title` 已写明。KITTI 全量 156 条**没有隧道**（相机帧已验证：城市峡谷/树冠/步行街/高速，无隧道），
  最长真实失锁 34.3s（0096）。
- **MM 能力边界（本次最有价值的实测）**：DR 横向漂移在**车道间距量级内**时 HERE 能纠正回主路
  （30s：漂 11m → 匹配 1 段 2594m，真值→匹配 mean 1.19 / max 6.10m）；超出后 HERE 会**跟着漂移匹配到旁路**
  （60s：漂 58.6m → 2 段 2431m，max 49.85m）。**这不是 HERE 不行，而是串行 DR→MM 架构的固有上限
  ——量产里 MM 要与 DR 紧耦合（map-aided DR）**。被问到「你的方案什么时候失效」时，这是最好的答案。
- **HERE 对「输入卡住」是鲁棒的**：把失锁期冻结流直送 HERE 得 1 段 2536m（它会当"原地等待"再桥接）。
  路线碎裂只由**噪声/跳变**引起（0093 的 4 段碎裂即此），不是因为"没数据"。
- **车头向上为何用 CSS 旋转而非 SDK API**：HERE JS API 3.1 的 `setLookAtData({ heading })` 和 `getViewPort().setHeading()`
  均依赖 Tangram WebGL 引擎的 `lookAtManipulator`。本机 WebGL 虽 Hardware accelerated 但 Tangram 内部 `getExtension()` 返回 null，
  导致 `Scene.load()` 失败、`lookAtManipulator` 为 null、heading 旋转静默失效。CSS `transform: rotate()` 绕过此限制，
  代价是 `scale(2.3)` 放大导致 marker 偏大（详见 spec `2026-09-12-demo-mode-navigation-design.md`）。

## 三、待决事项（需要你拍板）

1. **60s 能力边界要不要也做离线可演示？**
   现在 `public/fixtures/<driveId>.json` 一份轨迹只能存一个档位（已按 **30s** 录）。
   若要离线也演示 60s 边界，两条路：①fixture 文件名带档位（`<driveId>@t60.json`，改 `loadFixture` 拼名）；
   ②只在线演示 60s（有 key 时旋钮会重发请求，已支持）。**建议 ②**，零改动。
2. **`data/` 下的分析工具要不要留档？**（作品集可复现性问题）
   目前这些都**在 .gitignore 里、不在仓库**：`analyze_kitti.py`（`posmode` 列的源头，没有它 `public/sample/here/*.json` 无法复现）、
   `fetch_kitti_oxts.py` / `fetch_kitti_frames.py`（S3 Range 取数）、`scan_outage_candidates.py`（156 条全量扫描）。
   **仓库里没有任何东西能解释"这些轨迹是怎么来的"**。若要发表为作品集，建议把
   `analyze_kitti.py` + `scan_outage_candidates.py` 移到 `scripts/`（并放宽 .gitignore：`data/*` 但白名单这两个）。
   **这是我认为最值得做的一件**——否则面试官看到 `numsats`/`posmode`/`pos_accuracy` 只能靠猜。
3. **0093 要不要在 UI 上标注「真值不可信」？**
   它保留作对照，但失锁期真值自身 ±21m（max 44.3m）。若被追问「0093 的 26m 偏差是怎么算的」，
   需要能立刻答出「那 26m 里有真值自身 21m 的不确定度」。可选：在轨迹下拉项上标 `(真值不可信)`。
